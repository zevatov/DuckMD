> **Зачем этот файл:** единое место, где зафиксированы **все пожелания пользователя и ответы на уточняющие вопросы** из чата-обсуждения, с привязкой к требованиям (`SPEC.md`) и истории реализации (`CHANGELOG.md`). Другой агент не видит историю переписки — здесь собран контекст «почему так», чтобы ничего не потерялось.

> Единый источник версии — `MARKETING_VERSION = 0.6.15` в `project.yml` → `CFBundleShortVersionString` в `Info.plist` (история — в `CHANGELOG.md`). Упоминания 0.5.0/0.6.5/0.6.9 ниже — исторические (момент принятия решения), актуальная версия — 0.6.15.

## 1. Фундаментальные пожелания (из первого сообщения)

### D-1. Главная цель — мгновенный красивый просмотр MD ✅
> *«сделать супер быстрый мд ридер ... сейчас чтоб посмотреть мд файл с красивым форматированием мне надо открыть мд через вскод, ждать его загрузки, нажать на кнопку рендера расширить экран и уже прочитать отрендеренный мдшник»*

**Решение:** DuckMD открывает `.md` двойным кликом → рендер видим за **<1 секунды**, без загрузки редактора, без лишних кнопок. Это **главная ценность продукта** и критерий приёмки №1.
→ `SPEC §1`, `N-1`, `SPEC §7.1`

### D-2. Красивый, простой, с возможностью редактирования ✅
> *«сделать красивый и простой мд ридер чтоб был как заметки красивые и с доп возможностью редактирования»*

**Решение:** Вайб **Apple Notes** × Bear. Спокойная типографика (serif тело, sans заголовки), мягкие отступы, центрированная колонка чтения. Три режима: Просмотр / Правка (split) / Код.
→ `SPEC §1`, `UX §1`, `R-DOC`

### D-3. Стиль Apple, вкус, Liquid Glass ✅
> *«сталь и вайб эпл просто и со вкусом с ликвид гласс»*

**Решение:**
- **SwiftUI, macOS 26+** — нативный Liquid Glass доступен из коробки.
- Liquid Glass на тулбаре и поверхностях (баннеры, карточки хаба через `.glassEffect`/`.regularMaterial`).
- Минимализм «как от Apple»: ничего лишнего, спокойные цвета, мягкие скругления (8–12pt), плавные анимации (`.easeInOut(0.18)`).
- **Акцент жёлтый #FFC800** (цвет утки) — H1, чекбоксы, активные элементы.
→ `SPEC §1` (Вайб), `N-2`, `UX §1`, `ARCHITECTURE §1` (SwiftUI/Liquid Glass)

### D-4. Маскот и логотип — жёлтая уточка ✅
> *«название DuckMD - логотип и маскот тоже уточка должны быть такая минималистичная желтая в стиле эпл кароче все просто и во вкусом»*

**Решение:** Маскот — минималистичная жёлтая уточка. Реализована **векторно** в SwiftUI (`DuckLogo.swift`, через `Canvas`): тело + голова + клюв + глаз + блик. Иконка приложения 1024px сгенерирована скриптом (`scripts/generate_icon.swift`). Утка везде: хаб (header), About, пустое состояние.
→ `SPEC §1`, `R-BRAND-1..8`, `UX §6.4`

### D-5. Подробный план перед реализацией ✅
> *«составь подробный план по реализации проекта для начала спроси у меня пару вопросов уточняющий составь ТЗ и после его подтверждения реализуем»*

**Решение:** Сначала вопросы → ответы → подтверждение плана → реализация. Теперь этот процесс зафиксирован в документации.
→ этот файл + `SPEC`

## 2. Ответы на уточняющие вопросы (раунд 1)

### D-6. Технология: нативно под каждую систему ✅
> **Вопрос:** «На каком стеке делаем?»
> **Ответ:** *«вообще хотелось бы под каждую систему сделать чтоб оно выглядело на каждой системе нативно и максимально быстро и оптимизированно, я думаю универсального варианта не будет под это»*

**Решение:** **Нативный SwiftUI под macOS 26+** (не Electron/Flutter). Кроссплатформенности НЕТ — это осознанный выбор: для каждой ОС в будущем отдельный нативный проект (WinUI для Windows, GTK для Linux), ради скорости и «вкуса».
→ `ARCHITECTURE §1`, `SPEC §6` (границы), `N-3`

### D-7. Открытие файлов: ассоциация + всё остальное ✅
> **Вопрос:** «Как пользователь должен открывать .md файлы?»
> **Ответ:** *«ну вообще первый вариант [ассоциация] но поддержка всех остальных тоже круто будет»*

**Решение:** Реализовать **все способы**:
- Ассоциация `.md` → двойной клик открывает в DuckMD (`UTExportedTypeDeclarations`, `LSHandlerRank: Owner`). ✅ частично
- Drag & Drop файла на иконку/окно. (T-9)
- Quick Look-расширение. (P2, T-20)
- Закрепление в Dock (автоматически из AppIcon). ✅
→ `SPEC R-START-2`, `R-HUB-5`, `ARCHITECTURE §7`

### D-8. Редактирование: «три в одном», WYSIWYG + синхрон ✅
> **Вопрос:** «Каким должно быть редактирование?»
> **Ответ:** *«давай сделаем три в одном тоесть человек запускает мдшник и видит его красивым нажимает на какие то буквы и прям вписывает туда что то может без знания мд редактировать его и визуально и он красиво отрендерится правильно по синтаксису сам. Также область кода ... привязана к отрендеренной области ... они связаны и в прямом времени все меняется также весь синтаксис автоматом обновляется и дополняется чтоб небыло ошибок»*

**Решение (фазированное, согласовано с пользователем — D-9):**
- Фаза 1: мгновенный красивый просмотр + синхронный режим кода. ✅
- **Фаза 2: split-режим (Код + живой рендер рядом)** — «области связаны и в прямом времени всё меняется». Печатаешь слева → справа обновляется мгновенно через общий `document.text`. (T-1)
- **Автоформатирование** — снимает «незнание Markdown»: Enter в списке → новый пункт, `# ` → заголовок, авто-закрытие `**`, триггеры. ✅
- **WYSIWYG-lite (click-to-edit в рендере)** — заготовка есть (`InlineEditableText.swift`), интеграция отложена (P2, T-10), т.к. split+автоформат уже дают ощущение «редактирую красиво» надёжнее, чем contenteditable.
- «Синтаксис автоматом обновляется и дополняется» = автоформатирование + живой рендер.
→ `SPEC R-EDIT`, `R-DOC-3`, `UX §4.3`

### D-9. Фазирование разработки ✅
> **Вопрос:** «Согласен ли фазировать?»
> **Ответ:** *«Да, фаза 1 → потом WYSIWYG (Рекомендуется)»*

**Решение:** Сначала надёжный MVP (просмотр + код-режим), затем WYSIWYG сверху. Фаза 1 ✅ реализована.
→ реализация — `CHANGELOG.md`

### D-10. MVP: только базовый MD ✅
> **Вопрос:** «Какой набор фич для ПЕРВОЙ рабочей версии?»
> **Ответ:** *«давай пока только мд, в основном это сделан проект для упрощения взаимодействия с нейросетями и их отчетами и текстами финальными»*

## 3. Ответы на уточняющие вопросы (раунд 2 — для 0.5.0)

### D-11. Конвертер: из всех форматов ✅
> **Вопрос:** «Из каких форматов конвертировать В Markdown?»
> **Ответ:** *«давай все»*

**Решение:** Конвертация В MD из: `.docx`, `.pdf`, `.html`, `.rtf`, `.txt`. Точка входа — drag&drop в хаб или кнопка «Конвертировать». Реализация по форматам в `ARCHITECTURE §5.4`.
→ `SPEC R-CONV-1..5`, `UX §5`

### D-12. Хаб при старте; файл — напрямую, минуя хаб ✅
> **Вопрос:** «Как должно вести себя приложение при запуске (без открытого файла)?»
> **Ответ:** *«при открытии какого то именно файла то этот файл быстро без всяких доп рендеров с возможность нажатия кнопки назад и переходом в хаб, а при открытии приложения хаб»*

**Решение:**
- **Открытие приложения (без файла)** → открывается **хаб**.
- **Открытие конкретного `.md`** (двойной клик) → файл открывается **напрямую в режиме документа**, **без хаба**, **мгновенно**, без лишних рендеров.
- В режиме документа есть кнопка **«← Хаб»** (назад).
→ `SPEC R-START-1..4`, `UX §2`

### D-13. Внешнее редактирование: авто-обновление + таймер 5с на отмену ✅
> **Вопрос:** «Файл отредактирован снаружи. Как реагировать?»
> **Ответ:** *«давай автообновление но с таймером на 5 секунд где будет кнопка отменить и он предыдущую версию вернет»*

**Решение:**
- FSEvents мониторинг открытого файла.
- При внешнем изменении → **авто-обновление** содержимого.
- **Перед обновлением — мягкий баннер с таймером 5 секунд** и кнопкой **«Отменить»**.
- При «Отменить» → восстанавливается **предыдущая версия** текста (держится в памяти `MarkdownDocument.previousText`).
- По истечении 5с → авто-применение.
- Если есть несохранённые локальные правки → диалог «Перезаписать ваши правки?».
→ `SPEC R-EXT-1..5`, `UX §4.5`

## 4.5. Технические решения (очистка, v0.6.2)

### D-22. Удаление мёртвого SwiftUI-рендер-стека; рендер = WKWebView ✅
> **Решение владельца (Этап 3, финал R2):** УДАЛИТЬ.

**Статус:** Accepted · **Дата:** 2026-09-02

**Контекст:**
- Аудит (Этапы 0–2) выявил **двойной рендер-путь**: живой путь — WKWebView (`WebPreviewView` + `WebPreviewFactory` + `PreviewBridgeScript`), а SwiftUI-рендер остался мёртвым грузом.
- Мёртвые 4 файла (~390 строк), нигде не инстанцируются (подтверждено двумя аудитами + grep по всему воркспейсу: 0 ссылок в Swift-коде вне самих файлов):
  - `Views/RenderedMarkdownView.swift` (включая вспомогательные `BlockquoteView`, `ListView`, `CodeBlockView`, `TableView`)
  - `Parsing/MarkdownInlineRenderer.swift`
  - `Theme/MarkdownTheme.swift`
  - `Editing/InlineEditableText.swift`

**Решение:**
- Все 4 файла выведены из таргета: перемещены в `archive/dead-swift-render/` (вне `DuckMD/`, поэтому `xcodegen generate` их не подхватывает — sources в `project.yml` = папка `DuckMD`). Окончательное `rm` владелец выполняет сам позже; до тех пор файлы лежат в архиве воркспейса.
- **WKWebView — единственный рендер-путь** DuckMD.

**Последствия:**
- Доки `ARCHITECTURE.md`, хендофф-журнал (локальная запись, не публикуется), `UX.md` и запись D-8 содержат устаревшие упоминания выведенных из таргета файлов — **синхронизация доков отмечена как отдельная задача** (не в scope этого изменения).
- Возврат к SwiftUI-рендеру возможен **только как новая реализация с нуля**; архив — только справочная история, не для включения в таргет.

**Живой код не затронут:** `DuckLogo` (AppIconHelper, HubCardView, AboutView) остаётся.
→ `ARCHITECTURE §2`, `UX §4`, этот файл (D-8)

### D-23. Редизайн маскота и иконки на гранёный стиль (Low-Poly) — v0.6.5 ✅
> *«заменить лого моего приложения на какое то из этих трех уточек какую лучше поставить я склоняюсь ко второму варианту»*

**Решение:**
- Переход с плоской процедурной утки на **гранёную (low-poly) 3D-уточку**. Полигональная форма рифмуется с Markdown (структура, грани, синтаксические блоки), сохраняя премиальный Apple-стиль.
- Создан ассет высокого разрешения `DuckMD/Assets.xcassets/DuckLogo.imageset` с 32-битным RGBA без артефактов палитры.
- Сгенерирован полноценный системный `AppIcon.appiconset/icon_1024.png` со сквирклом Apple, тёплым градиентом бумаги и естественной тенью.
- `DuckLogo.swift` использует нативный `Image("DuckLogo")` с сохранением API.
→ `SPEC §1, R-BRAND-1..2`, `CHANGELOG.md`

### D-24. Исправление бага белого экрана (loadHTMLString) и Smart Centered Sync Scroll — v0.6.6 ✅
> *«почему тут баг рендера он не появляется просто... механика общего скролла и подгонка под размеры и расположение текста... чтобы код листался чуть медленнее чем рендер, но всё оставалось по центру»*

**Контекст и проблемы:**
1. При открытии Markdown-файлов из внешних директорий рендер WKWebView оставался белым экраном. Метод `loadFileURL(tempURL, allowingReadAccessTo: docDir)` падал в `WebKit` с ошибкой `kNWErrorDomainPOSIX 1` из-за отказа песочницы в расширении прав доступа на временную директорию `/var/folders/...`.
2. Синхронизация скролла через глобальную долю `scrollY / maxScroll` приводила к сильной рассинхронизации: блоки кода и таблицы имеют разную высоту строк в коде и в HTML-рендере. При этом верх ($y = 0$) и низ ($y = \text{maxScroll}$) не доводились до конца.
3. Фон WKWebView при открытии и смене темы мог вспыхивать белым цветом, нарушая Apple-эстетику тёмных и цветных тем.

**Решение:**
1. **Рендер:** Перешли на `loadHTMLString(html, baseURL: docDir)`. Локальные ассеты резолвятся относительно `docDir`, временные файлы не блокируются песочницей WebKit.
2. **Скролл-синк:**
   - Позиционирование центрируется по элементу, пересекающему оптический центр окна (`midY`).
   - Координатор передаёт кортеж `(line, offsetInLine, fraction)`.
   - Внедрена краевая доводка: $y \le 0.005 \implies 0$, $y \ge 0.995 \implies \text{maxScroll}$.
   - Двустороннее подавление эха через `isProgrammaticScroll` / `_isProgrammaticScroll`.
3. **Фон и типографика:**
   - `underPageBackgroundColor` синхронизирован с `RenderThemeOption.nsBackgroundColor(for: theme)`.
   - Apple-типографика: `-apple-system`, `SF Pro Text/Display`, `SF Mono`, `line-height: 1.65`, скруглённые карточки кода и таблиц (radius 10px).
→ `SPEC §3.3 R-DOC-3`, `ARCHITECTURE §5.5`, `CHANGELOG.md`

## 4.6. Дистрибуция и безопасность (Этап 0 адаптирован, v0.6.15)

### D-25. GitHub-flow с локальной подписью; без песочницы и без MAS — решение владельца ✅
> *«Developer ID отсутствует, дистрибуция только через GitHub с локальной подписью (ad-hoc / Apple Development) как типичный open-source Mac-проект»*

**Статус:** Accepted · **Дата:** 2026-09-13 · **Версия:** 0.6.15

**Контекст:**
- Этап 0 изначально требовал Developer ID + notarization для публичной раздачи. Платного Apple Developer Program у владельца нет, сертификат «Developer ID Application» отсутствует.
- `security/DuckMD.entitlements` — минимальный набор, `com.apple.security.app-sandbox` отсутствует осознанно: песочница ломала бы открытие `.md` из произвольных директорий, drag&drop в хаб/конвертер и резолв локальных изображений (`loadHTMLString(html, baseURL: docDir)`), а MAS-дистрибуция не планируется.
- Фактический канал — `scripts/build-test-dmg.sh` (локальная подпись Apple Development / ad-hoc + hardened runtime → versioned DMG `build/dist/DuckMD-<VERSION>.dmg`) → GitHub Releases. `scripts/build-release.sh` (Developer ID + notarization) — историческая заготовка на будущее, в текущем flow не используется.

**Решение:**
- Дистрибуция — только через GitHub Releases с локальной подписью (ad-hoc / Apple Development), без Developer ID и без notarization, как типичный open-source Mac-проект (N-8 в `SPEC.md`).
- Установка из GitHub требует Gatekeeper-обхода (правый клик → Открыть / `xattr -dr com.apple.quarantine`) — инструкция в `README.md` § «Установка из GitHub».
- Отсутствие песочницы — осознанный risk-acceptance владельца: приложение работает без изоляции, с полным доступом к файловой системе пользователя; компенсация — отсутствие сети/телеметрии (N-6), экранирование raw HTML (Этап 0), валидация JS-payload в `ContentView.validatedEditPayload`, hardened runtime включён (`ENABLE_HARDENED_RUNTIME` в `project.yml`).
- Раздача через MAS исключена (песочница + review не нужны для текущей аудитории).

**Последствия:**
- G-3 закрыт через GitHub-flow; чек-лист Developer ID сохранён как историческая заготовка.
- При появлении платного аккаунта — вернуться к `scripts/build-release.sh` (Developer ID + notarization + staple) отдельным решением; песочницу при этом НЕ включать без пересмотра D-25 (сломает файловые сценарии).
→ `SPEC N-8`, `ARCHITECTURE §10.1`, `README.md` § «Установка из GitHub», `security/DuckMD.entitlements`

## 6. Принципы, выведенные из пожеланий

1. **Скорость превыше всего** — мгновенность открытия это не фича, а суть продукта. Любое решение, замедляющее старт, отвергается.
2. **Нативность и вкус** — выглядит как приложение от Apple, не как Electron. Liquid Glass, системные шрифты, мягкость.
3. **Простота для пользователя** — можно редактировать без знания Markdown (автоформатирование + живой рендер).
4. **Надёжность > модность** — предпочтение проверенным решениям (split+автоформат вместо хрупкого contenteditable WYSIWYG).
5. **Документация как продукт** — будущий агент должен по документации понять всё без вопросов.
